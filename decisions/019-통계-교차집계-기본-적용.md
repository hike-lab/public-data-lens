# ADR-019: `axis=org` 통계에 교차 집계를 기본 적용한다 — 클라이언트가 캐시하는 것과 캐시하지 않는 것

- 상태: 채택
- 날짜: 2026-08-25
- 관련: ADR-015(orgMatch·breakdown 신설 — 본 ADR이 그 기본값 결정을 개정), ADR-014(배포 트레인)
- 계기: v1.2.0-beta 배포 직후, 여러 MCP 호스트가 "교차 집계 기능이 없다"고 답한 관측

## 맥락

ADR-015로 `get_catalog_stats.breakdown`을 신설하고 2026-08-25 배포했다. 그런데 배포 직후
서로 다른 MCP 호스트가 같은 질문에 이렇게 답했다.

> 현재 통계 도구는 기관별 건수와 메타데이터 완전성을 각각 집계할 뿐,
> `기관 × 완전성` 교차집계를 제공하지 않습니다.

> 현재 `org` 검색이 부분 일치이기 때문입니다. (…) 기관 필터가 부분 일치 방식이라
> '본청만' 같은 조직 계층 질의를 처리하지 못하는 사례로 볼 수 있습니다.

**환각이 아니다.** MCP 호스트는 커넥터 연결 시점에 `tools/list`로 도구 목록을 받아
호스트 앱에 보관한다. 배포 전에 연결한 클라이언트의 목록에는 `breakdown`·`orgMatch`가
없으므로, 모델은 자기가 가진 명세를 정직하게 읽고 "그 기능 없음"이라고 답한다.
낡은 명세와 없는 기능은 겉보기에 구분되지 않는다.

개발 과정에서 우리 자신도 같은 함정에 빠졌다 — 배포 확인 중 캐시된 연결로 `get_context`를
호출해 `2026-06`을 받고 "MCP가 구 릴리스를 서빙한다"고 오진했다(직접 호출로는 `2026-07`).

**프로토콜 차원의 해결은 불가능하다.** `notifications/tools/list_changed`가 규격에 있으나
서버는 `tools.listChanged: false`이며, `stateless_http`에 배포 시 컨테이너가 교체되므로
알림을 보낼 살아 있는 연결 자체가 없다. **재연결이 유일한 방법이다.**

## 결정

**클라이언트가 캐시하는 것과 캐시하지 않는 것을 구분해 설계한다.**

```
입력 파라미터 추가        → 캐시에 걸린다   → 재연결 전까지 보이지 않는다
응답 필드 추가            → 걸리지 않는다   → 즉시 반영
데이터 갱신·전송 계층 변경 → 걸리지 않는다   → 즉시 반영
```

**`axis=org`는 `breakdown` 미지정 시 `completeness`를 기본 적용한다.** 기존 클라이언트가
이미 가지고 있는 `axis=org` 호출만으로 기관 비교가 가능해진다. 실제 적용값은 응답
`breakdown` 필드에 표기해 자기 서술적으로 만든다(`catalog-stats-breakdown-v1.0`).

**`breakdown="none"`으로 기본 적용을 끌 수 있다.** 응답 크기 때문이다.

| 호출 | 크기 |
|---|---:|
| `axis=org&limit=30` (기본 적용) | 5,722 B |
| `axis=org&limit=30&breakdown=none` | 1,959 B |
| `axis=org&limit=200` (기본 적용) | 32,615 B |
| `axis=org&limit=200&breakdown=none` | 10,395 B |

`limit=200`에서 22KB 차이는 호스트 LLM의 컨텍스트에 무시할 수 없다(v1.7.0에서 검색
기본 pageSize를 20→10으로 줄인 것과 같은 고려). `none`은 이 값을 아는 클라이언트만
쓰므로 기존 연결에 영향이 없다.

`axis=theme`에는 기본값을 두지 않는다 — 실사용 요구가 확인된 것은 기관 비교뿐이다.

## ADR-015의 결정을 개정하는 근거

ADR-015 시점의 수용 테스트는 이렇게 못박고 있었다.

```python
# breakdown 미지정 시 기존 응답 형태 불변(하위 호환)
assert "breakdown" not in r["data"]
```

의도는 소비자를 놀라게 하지 않는 것이었고 당시로는 타당했다. **개정 근거는 새 증거다** —
ADR-015는 2026-08-09에, 배포 전에, 호스트 캐시 문제를 모르는 상태로 쓰였다. 배포 후
실제로 관측된 것은 "놀라움"이 아니라 "기능이 닿지 않음"이었고, 제보자가 가장 활용도가
크다고 꼽은 항목이 바로 이것이다(Issue #1 제안 1).

계약 정합성은 확인했다 — 응답 스키마의 `buckets[].items`는 `required: [key, count]`이며
`additionalProperties: false`가 없다. 필드 추가는 호환성 정책상 additive(minor)다.

## 계약 영향

`SCHEMA_VERSION`은 1.8.0을 유지한다. 입력 스키마에서 바뀐 것은 `breakdown` **설명 문안**
뿐이고(`none` 언급 추가), 응답 필드 추가는 additive다. 명세 재생성 결과 변경은
`generatedAt` + 설명 2곳이다.

## 기각한 대안

- **`tools.listChanged: true`로 자동 갱신** — 알림을 보낼 지속 연결이 없다. SDK·호스트
  지원도 제각각이다.
- **`org` 부분일치 기본 동작 변경**(정확일치를 기본으로) — 기존 소비자의 결과 건수가
  8,957 → 3,317로 바뀐다. 응답 필드 추가와 달리 이건 진짜 breaking이다.
- **`limit`이 작을 때만 기본 적용** — 임계값이 마법이 된다. 명시적 `none` 옵트아웃이 낫다.
- **재연결 안내만 하고 기본값은 그대로** — 일반 이용자는 안내를 읽지 않고, 읽어도
  "왜 내가 이걸 해야 하나"가 된다. 서버가 흡수할 수 있으면 흡수하는 것이 맞다.

## 후속

- 연결 안내 페이지에 재연결 고지를 넣었다(`ConnectView`, 일반 이용자용 문안).
- `orgMatch`는 입력 파라미터라 흡수할 방법이 없다. 다만 부분일치 결과에 하위 기관이
  섞였을 때 `warnings[]`로 알리는 방안이 남아 있다(응답 필드이므로 즉시 반영 가능).
  현재는 `EXACT` 0건에만 경고가 있고 혼입 시에는 침묵해 비대칭이다 — 별건으로 검토.
- **앞으로 새 기능을 설계할 때 이 구분을 먼저 본다.** 응답 필드로 표현할 수 있는 것을
  입력 파라미터로 만들면, 배포해도 기존 이용자에게 닿지 않는다.
