# ADR-011: 데이터 계열(dataset family) 개념 도입 — 후보 사전계산 계층

- 상태: 채택 (P0 — 서버 내부 사전계산만. MCP·웹 노출은 별도 게이트)
- 날짜: 2026-08-05
- 관련: ADR-005(Relations 렌즈 기각 — 본 ADR이 그 기각 사유를 부분 해소), ADR-004·006(additive 계약 절차)

## 맥락

2026-06 스냅샷 전수(96,056건)와 구조 관측(59,395건, 파일형의 71%)을 대조한
실증 분석에서 다음이 관측됐다.

- 하나의 실질적 데이터가 연도·지역·시설·품목 단위로 여러 목록에 분리 등록된
  계열 후보가 세 가지 결정론 신호의 합집합으로 파일형의 17.8%(14,930건,
  후보 3,426개)에서 탐지됐다. 탐지 규칙별로는 2.4~7.9%다. 이 수치는 사람
  검증 전 후보 비율이며 확정된 파편화 비율이 아니다.
- 후보의 41.8%는 구성원이 동일 구조지문까지 공유한다. 동일 구조지문 공유의
  71%는 같은 기관 내 현상이다(표준 서식 가설로 설명되는 것은 29%뿐).
- 대표 사례: 제주 무장애여행 관련 301개 목록(실측 합계 1,970행). 개별 목록만
  보는 사용자·AI는 계열의 전모를 알 수 없다.
- 현행 목록 체계에는 파편 간 관계를 표현하는 필드가 없다. DCAT 3(2024)는
  이 문제를 위해 `dcat:DatasetSeries`를 도입했으나, 현행 기반 DCAT-AP-KR
  (DCAT-AP 2.1 기반)에는 계열 개념이 없다.

프레임: **현상은 데이터셋 파편화, 제도적 맹점은 파편 간 관계의 부재, 대안은
목록 폐지가 아니라 데이터 계열의 복원이다.** 목록은 행정적 등록·책임의
단위로 유지된다.

## 결정

1. **월별 빌드에서 계열 후보를 사전계산**한다(`pipeline/families.py`,
   rule: `family-candidate-v1.0`). 요청 시점 계산 없음. 릴리스 DB에
   `families`·`family_members` 테이블로 적재한다(additive — 기존 테이블·계약
   무변경).
2. **후보는 판정이 아니다.** 모든 후보는 `evidence_level`(CATALOG_ONLY |
   PLUS_STRUCTURE)과 `review_status`(UNREVIEWED | CONFIRMED_FAMILY |
   LEGITIMATE_SPLIT | NOT_A_FAMILY)를 동반한다. `relation_type`은 자동
   추정값(TIME_LIKE | REGION_LIKE | NUMBERED | NAME_PARTITION)이다.
3. **family_id는 구성원 집합의 해시**로 결정론 귀속된다. 구성이 바뀌면 id가
   바뀌어 사람 검증 상태가 다른 구성의 계열로 잘못 승계되지 않는다.
4. **사람 검증은 수동 관리 파일**(`data/catalog/family_reviews.json`)로
   병합한다 — `withdrawn_confirmed.json` 전례를 따른다. 층화표본 200건
   검증시트 판정 결과가 첫 입력이 된다.
5. **노출 게이트**: MCP 노출(P1, 계약 v1.7.0 minor — `get_dataset`의
   `familyCandidate` 블록과 `get_catalog_stats` 계열 통계의 additive 추가)은
   사람 검증 정밀도 산출 후에만 배포한다. 웹 표면(P2)은 ADR-005 재심을
   별도 ADR로 선행해야 한다.
6. **계약 의미**(P1에서 CLAUDE.md 의미 표에 등재할 정본):
   - `UNREVIEWED` 후보는 자동 탐지다. 확정된 계열이 아니다.
   - `LEGITIMATE_SPLIT`은 정당한 분리다. 파편화가 아니다.
   - 계열 후보의 존재는 문제 신호가 아니다 — 실패색·경고색 금지.
   - 관측 스토어 부재 시 구조 신호 없이 CATALOG_ONLY로 강등된다(미관측은
     불일치가 아니다).

## 기각한 대안과 이유

- **계열을 확정 단위로 승격(목록 대체)**: 파일형의 82%는 계열 신호가 없는
  단독 목록이고, 선행 평가(Track E)에서 자동 병합의 멤버 오병합 60%가
  실증됐다. 강제 통합은 신고 책임·이력의 귀속을 깬다. 계열은 목록 위의
  관계 뷰로만 존재한다.
- **요청 시점 실시간 탐지**: 96k 레코드 전역 클러스터링은 응답 시간과
  재현성(§2 결정론 판정) 모두를 해친다. 월별 사전계산이 구상 문서 §8과
  일치한다.
- **유사도 점수(임베딩·문자열 거리) 기반 탐지**: 재현 불가·버전 관리 불가.
  레지스트리의 다른 규칙들과 동일하게 결정론 규칙만 사용하고, 규칙 확장은
  버전 증가를 동반한다.
- **즉시 MCP 노출**: 부정확한 계열 제공은 해석 편차를 줄이는 게 아니라
  늘린다(제품 철학 역행). 검증 정밀도가 게이트다.

## 영향

- 빌드: 탐지 단계 추가(수 초 수준). 관측 스토어가 빌드 입력이 되는 첫
  사례 — 부재 시 자동 강등으로 빌드는 실패하지 않는다.
- 계약: P0은 무변경. P1에서 v1.7.0(minor, additive) + `gen_tool_spec.py`
  재생성 + `test_contract_spec.py` 갱신.
- 검증 루프: 검증시트 판정 → `family_reviews.json` → 다음 빌드에 반영 →
  판정 케이스는 `evals/`에 축적(코드북 v1.1).
- 표준 환류: 운영 실적을 근거로 DCAT-AP-KR 차기 버전에 DatasetSeries
  프로파일을 제안한다(발행 주체: HIKE Lab).
- 알려진 한계: '버전' 관계는 현 신호(2-스냅샷 diff·제목 표기)로는 탐지력이
  약해 v1.0 유형에서 제외했다. 관측 커버리지 71%의 편향이 evidence_level
  분포에 전이된다(CATALOG_ONLY가 과대해질 수 있음).
