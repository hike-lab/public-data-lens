# ADR-007: 홈 검색 단독화 — 쇼케이스는 '둘러보기', 투명성은 '소개'로

- 상태: 채택 (2026-08-04)
- 날짜: 2026-08-04

## 맥락

가이드 §3은 홈을 9블록(Hero·검색·서사·해부·Live·Coverage·인프라 등)으로 명세했고
STEP 6~9에서 그대로 구현했다. 그러나 소유자 검토(2026-08-04): "메인 화면은 검색으로
시작하는데 이 아래 기능이 다른 내용을 제공할 필요가 있을까 — 중요하면 별도 메뉴로."
검색이 주 행동인 화면에서 아래로 계속 이어지는 블록은 초점을 흐린다.

## 결정

- **홈 = 검색 단독**: 워드마크·히어로(축소)·검색바 3모드·예시·전체 목록 버튼으로 끝.
- **'둘러보기'(/explore) 신설**: 서비스가 데이터를 어떻게 읽는지의 쇼케이스 3블록 —
  탐색 서사(§3 #3)·데이터 해부(§3 #5)·구조 관측 실물 3건(§3 #4). 자체적으로
  검색 1회를 호출해 채운다(기존 응답 원칙 유지). 서사 CTA는 홈 목적 모드로
  URL 이동(`/?mode=purpose&purpose=…` — ADR-003 복원 경로 재사용).
- **투명성 블록(Coverage·Open Infrastructure)은 '소개' 하단으로**: 2차 UX 검토의
  "카탈로그 현황은 소개로" 권고와도 일치. 신뢰 근거는 서비스 설명 옆이 제자리다.
- 상단 메뉴: 둘러보기 · 소개 · MCP 연결(전부 동일 링크 형식). 변경 이력은 푸터.

이 결정은 가이드 §3의 "홈 9블록"을 **"홈 1블록 + 둘러보기 3블록 + 소개 2블록"으로
재배분**한 것이다 — 블록 자체와 데이터 출처 원칙(기존 서버 응답으로만 채움)은 불변.

## 기각한 대안

- 홈 하단 유지 + 접기: 접힌 블록은 존재 이유가 약하고 홈 초점 문제를 해결하지 못함.
- 블록 삭제: §3의 각 블록은 차별점(과정·해부)과 신뢰(투명성)를 담당 — 위치의 문제이지
  존재의 문제가 아니다.

## 영향

- DESIGN.md §3 정보 구조 갱신 동반. 홈 이탈 없이 검색 시작까지의 시각 소음 최소화.
- ExploreView가 검색 1회를 추가 호출(홈에서는 제거된 것과 상쇄).
