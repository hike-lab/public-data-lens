# 010. 프로젝트 경계 및 자산 흐름

- 상태: 채택
- 일자: 2026-08-04
- 관련: `009-저장소-통합-및-이력-미이월.md`

## 맥락

세 개의 산출물이 인접해 있으나 소속과 성격이 다르다.

| 산출물 | 성격 | 과제 범위 | 주체 |
| --- | --- | --- | --- |
| AIRD 표준안 | 표준 문서 | **범위 안** | 연구실 / 과제 |
| 공공데이터 렌즈 | 오픈소스 (MIT) | 범위 밖 | `hike-lab` 조직, 공개 무료 서비스 |
| AI 컨시어지 | 상용 서비스 | 범위 밖 | 별도 법인(스타트업) |

세 산출물의 실무 담당이 사실상 겹친다. 경계가 문서화되지 않으면 다음 질문에 사후 설명으로 답해야 하고, 사후 설명은 사전 기록보다 설득력이 낮다.

- 공개 서비스가 특정 사업자의 상용 제품 인프라로 쓰이고 있는가
- 표준 제정 참여자가 그 표준 위의 상용 제품을 갖는 것이 고지되었는가
- 과제 범위 밖 산출물이 과제 자원으로 개발되었는가

렌즈와 컨시어지가 처음부터 별도 GitHub 계정으로 분리되어 있던 것은 이 경계 의도의 표현이었으나, 그 의도 자체는 어디에도 기록되지 않았다. ADR 001로 저장소를 통합하면서 계정 분리라는 암묵적 표현이 사라지므로, 경계를 명문화할 필요가 생겼다.

## 결정

### 1. 자산 소유

| 자산 | 소유 |
| --- | --- |
| `glossary/`, 판정 규칙, JSON-LD Context, SHACL | 렌즈 (컨시어지는 참조만) |
| `evals/` 판정 케이스 | 렌즈 |
| 컨시어지 프롬프트·분석 워크플로 | 컨시어지 |
| 미충족 요구 로그 | 컨시어지에서 수집 → 아래 4항 조건으로 렌즈 환류 |

### 2. 컨시어지의 렌즈 접근 — 특혜 접근 금지

컨시어지는 렌즈를 **공개 MCP 계약을 통해서만** 소비한다. 내부 DB 직접 접근, 비공개 엔드포인트, 미공개 스냅샷 선행 접근을 하지 않는다.

운영 방식은 **컨시어지 측 셀프 호스팅**을 원칙으로 한다. MIT 라이선스이므로 상업적 셀프 호스팅에 제약이 없으며, 공개 서비스의 rate limit(IP당 2 req/s)에 걸리지 않고 공개 서비스에 부하를 주지 않는다. 부수 효과로 셀프 호스팅 절차의 동작이 지속적으로 검증된다.

### 3. 표준과 렌즈의 의존 방향 — 렌즈가 선행 구현

렌즈는 **표준안의 산출물이 아니라 독립적 선행 오픈소스 구현**이다. 표준 논의에 대한 기여 방향은 `렌즈 → 표준`이며 역방향이 아니다. README의 연구 포지셔닝을 이 방향으로 서술한다.

> 본 서비스는 AIRD 표준 논의에 앞서 개발된 독립 오픈소스 구현이며, 표준안의 실현 가능성을 검증하는 참조 구현으로 활용됩니다.

첫 공개 배포에 부여하는 릴리스 태그(`v1.1.0-beta`)와 CITATION.cff·DOI가 **해당 시점에 이 산출물이 MIT로 존재했다는 날짜 증빙** 역할을 겸한다.

### 4. 환류 범위 — 고객 데이터는 환류하지 않는다

컨시어지가 상용 서비스이므로 사용자 질의는 고객 데이터다. 환류 가능 범위를 다음으로 제한한다.

| 환류 대상 | 가능 여부 |
| --- | --- |
| 고객 질의 원문 | 불가 |
| 추상화된 목적 패턴 + 미충족 데이터 항목 | 가능 (이용약관 근거 필요) |
| 집계 통계 ("이 유형 목적의 n%가 미충족") | 가능 |

컨시어지 이용약관에 익명·집계 형태의 개선 기여 조항을 **서비스 개시 시점부터** 포함한다. 사후 추가는 기존 고객에게 소급 적용되지 않는다. `evals/cases`의 `provenance.source`에 `concierge_derived` 값을 추가해 출처를 구분한다.

### 5. 이해관계 고지

렌즈 README에 상용 컨시어지의 존재와 특혜 접근 부재를 명시한다.

> 이 서비스를 기반으로 하는 상용 AI 컨시어지가 별도 법인에서 제공됩니다. 렌즈는 MIT 라이선스로 누구에게나 동일하게 공개되며 특정 사업자에게 우선 접근을 제공하지 않습니다.

### 6. 컨시어지 저장소

별도 법인의 GitHub 조직 계정 아래 private으로 둔다. 개인 계정과 연구실 조직 계정을 모두 사용하지 않는다. 이름은 렌즈의 파생물로 읽히지 않는 독립 브랜드로 하고, 렌즈는 upstream 오픈소스로 문서에 밝힌다. 이름 확정 전이라도 빈 저장소로 자리를 선점한다.

## 기각한 대안과 이유

### A. 컨시어지를 연구실 조직(`hike-lab`) 아래 private으로 개발

기각 이유: 상용 서비스를 연구실 조직 아래 두면 소유권과 기여 이력이 엉킨다. 컨시어지는 과제 범위 밖이고 학교 직무발명 범위 밖이라는 판단과 저장소 위치가 모순된다.

### B. 컨시어지를 개인 계정에서 개발 (기존 방식 유지)

기각 이유: 직무발명 범위를 다투는 상황에서 개인 계정은 가장 방어하기 어려운 위치다. 개인이 만들었다는 사실 자체가 직무발명 판단의 쟁점이므로, 계정 분리는 경계를 **약하게** 표현한다. 또한 법인 자산이 개인 계정에 있는 구조는 투자·실사에서 지적된다.

### C. 컨시어지가 렌즈 내부 DB·비공개 엔드포인트에 직접 접근

성능과 구현 편의에서 유리하다.

기각 이유: 공개 서비스를 특정 사업자의 제품 인프라로 쓰는 구조가 되어 결정 2·5항의 근거가 무너진다. 또한 렌즈 MCP 계약의 **첫 외부 소비자**라는 실증 증거를 상실한다. 계약 v1.0.0으로 실제 애플리케이션이 만들어진다는 사실은 표준 제정에서 값나가는 논거이므로, 구현 편의보다 우선한다.

### D. 컨시어지 사용 로그를 그대로 evals로 환류

가장 값나가는 실사용 판정 케이스가 여기서 나온다.

기각 이유: 상용 서비스의 사용자 질의는 고객 데이터이며 공개 저장소에 넣을 수 없다. 결정 4항의 추상화 단계를 거친다.

### E. 렌즈를 AIRD 표준안의 구현체로 서술

기각 이유: 표준안이 과제 산출물이므로, 렌즈를 그 구현체로 서술하면 "렌즈는 과제 범위 밖"이라는 판단과 긴장 관계가 생긴다. 선행 구현으로 서술하면 기여 방향이 명확해지고 연구 포지셔닝도 유지된다.

## 영향

- README 개정 2건: 연구 포지셔닝 문구를 선행 구현으로 변경, 이해관계 고지 추가.
- 컨시어지 개발 착수 전 이용약관에 환류 조항을 포함해야 한다. 착수 후 추가는 소급되지 않는다.
- `evals/schema/case.schema.json`의 `provenance.source` enum에 `concierge_derived` 추가.
- 컨시어지는 렌즈 셀프 호스팅 절차에 의존하므로, 배포 설명서의 정확성이 컨시어지 운영 리스크가 된다.
- 렌즈 MCP 계약의 하위 호환 파기는 컨시어지 장애로 직결된다. 계약 v1.0.0 동결 원칙의 실질적 구속력이 커진다.
- 과제 협약·학내 규정 해석은 본 ADR의 범위가 아니다. 담당 부서의 판단을 전제로 하며, 본 문서는 그 판단을 문서로 뒷받침하는 실무 조치를 기록한다.
